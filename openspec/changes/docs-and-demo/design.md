## Context

`README.md` today is a short grammar note written during v1. The `web-renderer` change produces a standalone build that can render charts on any page, which makes a real demo possible. The Obsidian community plugin submission is reviewed by people and a bot; they look for a clear README, a license, and a release. The repository will become public, so the README is also the landing page.

## Goals / Non-Goals

**Goals:**
- One README that serves users of the plugin, users of the library, and reviewers.
- A demo page where a visitor can type a chart and see it render, with no install.
- Images that are generated from the real renderer so they never lag behind.
- Everything deploys from `main` with no manual step.

**Non-Goals:**
- A docs framework (VitePress, Docusaurus). One HTML page, one script, one stylesheet.
- Hosting anything other than static files.
- Screenshots of the Obsidian app itself in CI. Those are taken by hand once and stored under `docs/img/obsidian/`; the generated images cover the rendered charts.

## Decisions

**Plain `docs/` folder on GitHub Pages, built by a workflow.** The page needs `dist/coolchordsheets.js`, which is gitignored. A Pages workflow runs `npm ci`, `npm run build:web`, copies `dist/` into the upload artifact next to `docs/`, and deploys. Committing `dist/` into `docs/` was rejected for the same reason as in the web-renderer design: noisy diffs on every source change. The page references the library as `./dist/coolchordsheets.js`, so opening `docs/index.html` locally works after a build by symlinking or copying `dist/` into `docs/` (the `npm run demo` script does this).

**Live editor is a textarea plus `render` on input.** The standalone library already exposes `render(text, container, options)`. The demo script listens to `input`, renders into a container, and shows diagnostics through the renderer's own list. The textarea starts with the "All of Me" chart. Toggles for show holds and uneven markers and a font size slider map to the options. Debounce is unnecessary; parsing 200 bars takes under 10 ms. The editor state is not persisted or shareable (non-goal).

**Screenshots by script.** `scripts/screenshots.mjs` bundles a small page with esbuild (same approach used during v1 verification), opens it with headless Chrome at a fixed width and device scale factor 2, and writes PNGs to `docs/img/`. The README links to those same files with raw GitHub URLs so the README on GitHub and the Pages site share images. Chrome path is taken from `CHROME_PATH` or the default macOS and Linux locations; if none exists the script exits 0 with a message so `npm test` and CI are never blocked by it. Screenshots are committed; the script is run by hand when the renderer changes, and a CI step diffs nothing (image diffs are flaky across platforms).

**README structure follows what the Obsidian reviewers read.** Order: one-sentence description, screenshot, install (community, BRAT, manual), quick start fence, grammar reference, chord symbols, settings, using on a web page, development, license. The grammar reference is the same content the demo page shows, kept in the README as the single source; the demo page links to it rather than duplicating it.

**LICENSE and CHANGELOG.** MIT, as `package.json` already states. CHANGELOG uses Keep a Changelog headings with a 0.1.0 entry; the release process (a later change) will read from it.

## Risks / Trade-offs

- [Pages workflow needs the repository to be public or Pages enabled] -> The change can be implemented and checked locally with `npm run demo`; deployment is verified after the repository is created.
- [Screenshots drift from the renderer] -> They are generated by a script from the example charts, and the README says which script produced them. A `docs:check` step verifies the referenced image files exist.
- [Demo page CSS conflicts with the chart stylesheet] -> The chart stylesheet is scoped under `.ccs-sheet`; the demo stylesheet only styles its own layout classes.
- [Manual Obsidian screenshots go stale] -> Only two are needed (reading mode, settings tab); they are labelled with the plugin version in the file name.
